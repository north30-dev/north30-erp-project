## 1. 背景与问题清单

菜单管理优化（07 号文档）收尾前后端联调时，发现以下系统性问题（按严重程度排序）：

| # | 问题 | 现状 | 影响 |
|---|------|------|------|
| P1 | 菜单停用自锁死循环 | 权限装载链路（`UserAccessServiceImpl.listMenuTree/listPerms`）对 admin 与普通用户均过滤启用状态；状态修改唯一入口是菜单管理页自身。停用「系统管理」目录或「菜单管理」菜单后，admin 也失去入口与权限点，无法从 UI 恢复，只能改库 | 单次误操作即可瘫痪整个管理端，属设计缺陷 |
| P2 | 超级管理员不可授予、不可区分 | `sys_user.is_admin` 仅由 AdminInitializer 给内置 admin 账号设置，无接口可改，新建用户恒为 0；「超级管理员」角色（`is_builtin=1`）只是普通角色，特权语义（全量权限、绕状态过滤）只认 `user.is_admin`，不认角色 | 全系统仅一个超管孤例，密码丢失即灾难；给用户勾「超级管理员」角色得到的只是当时勾选的菜单，新菜单需重新勾选，且不参与任何特权；超管与普通管理员在角色层面无区分度 |
| P3 | 启用/停用交互与实现不统一 | 用户管理：表格 `a-switch` + 专用接口 `POST /users/{id}/status`（实体充血 `changeStatus` + 18012 保护）；角色管理：表格 `a-switch` 但**假开关**——前端拼全量 updateRole 模拟；菜单/部门管理：纯文本标签，只能进编辑弹窗改 radio | 同类操作两套心智模型；角色页语义混杂（改状态走「编辑资料」接口）、权限粒度粗、乐观锁冲突概率高 |
| P4 | 内置菜单无保护标记 | `sys_menu` 无 `is_system` 类字段；内置种子菜单（/system 子树）可被随意停用、删除（未被角色引用时），与 `sys_config.is_system`、`sys_role.is_builtin`、`sys_user.is_admin` 的既有保护模式不对齐 | P1 的帮凶；误删/误停内置权限点无任何拦截 |
| P5 | 排序字段半成品 | 菜单域查询无 `orderBy`（`listEnabled` 等按自然序返回），表格却展示「排序」列——**展示了但没按它排**；新增时 sort 缺省全 0，同级顺序退化为 id 序，排序字段失效；纯列表（角色）的排序号无业务语义却同样维护 | 展示无效字段误导用户；垃圾缺省值；多余维护成本 |

## 2. 已确认的方案（唯一事实源）

### 2.1 三层角色模型（解 P2，并为 P1 的超管兜底铺路）

| 层级 | 角色 | 权限语义 | 特权 | 内置保护 |
|------|------|---------|------|---------|
| 超管 | `ADMIN`（超级管理员，`role_code` 固定 `'ADMIN'`） | **不依赖勾选**——代码层判定：全量权限 + 绕状态过滤 + 免疫自锁 | 可分配 ADMIN 角色；可编辑其他角色 | `is_builtin=1`：不可删/不可停用/权限集不可改（不走勾选，改了无意义） |
| 普通管理员 | `SYSTEM_ADMIN`（系统管理员，新增内置角色，预勾选全部 /system 菜单） | 完全由角色勾选的菜单决定 | 无特权：受状态过滤约束、不可停用/删除内置菜单、不可分配 ADMIN 角色 | `is_builtin=1`（不可删/停用），权限集可改（超管按需收放） |
| 业务角色 | 采购员、财务经理等（自建） | 角色勾选的业务菜单 | 无 | 自建，全生命周期可管理 |

关键规则：

- **超管判定**：`user.is_admin=1 || 持有 role_code='ADMIN' 的启用角色`。内置 admin 账号默认持有 ADMIN 角色（AdminInitializer 幂等保证），引导身份与角色身份并存。
- **提权守卫**：分配角色接口仅超管可分配 ADMIN 角色（否则任何可操作角色分配者均可自我提权）；ADMIN 角色权限集修改被拒。
- **普通管理员授权流程**（标准 RBAC，机制已存在）：角色管理 → SYSTEM_ADMIN 分配菜单（勾选 /system 页面与按钮权限点）→ 用户管理 → 分配角色。收权改勾选，细分多建角色（如只读管理员仅勾 list/detail 按钮）。

### 2.2 内置菜单保护（解 P4，P1 的源头防线）

- `sys_menu` 新增 `is_system` 字段（SMALLINT，0/1，对齐 `sys_config.is_system` / `sys_role.is_builtin` / `sys_user.is_admin` 模式）。
- **内置范围**：全部内置 /system 种子子树置 1（**含按钮节点**——按钮承载权限点，停用=无感知收回权限）。规则一句话：「种子菜单即内置菜单，全部保护」。后续采购/销售等模块的种子菜单同样置 1，写入数据库设计文档作为通用约定。
- `is_system` 是行级标记，**不随父级继承**：用户在 /system 下自建的业务菜单仍为 0，可正常停用/删除。
- 守卫（实体充血，收敛在 `SysMenu`）：
  - `is_system=1` 拒绝停用（新错误码 18039「内置菜单不可停用或删除」——18029/18030 已被字典域占用，顺延分配）；
  - `is_system=1` 拒绝删除（同 18039）；
  - 停用任意节点前检查子树是否含 `is_system=1` 节点（防停用父目录级联锁死内置子节点），命中同样拒绝。
- 前端：状态开关/编辑 radio/删除按钮对内置行禁用 + tooltip「内置菜单不可停用/删除」，与内置角色、admin 用户同一模式。

### 2.3 admin 绕过状态过滤（解 P1 的根本兜底）

- `UserAccessServiceImpl.listMenuTree/listPerms` 的超管分支改为取**全量菜单（含停用）**，不过滤 menu.status；普通用户分支维持现状（启用过滤是预期行为）。
- 效果：即使误停用任何菜单，超管依然可见、可进、可重新启用——自锁对超管不可能成立；普通管理员被锁由超管修复（存在「万能钥匙」即可接受）。

### 2.4 AdminInitializer 启动复位（恢复通道，顺带修数据）

- 启动时幂等复位：`is_system=1` 的菜单强制 `status=1`；内置 admin 账号确保持有 ADMIN 角色。
- 顺带修复当前库中已被停用的内置菜单数据。

### 2.5 状态开关统一（解 P3）

- **交互统一**：有启用语义的列表（用户/角色/菜单/部门），状态列一律 `a-switch`（受保护数据 disabled + tooltip）；编辑弹窗内保留 radio 用于创建时初始选择。
- **后端统一**：role/menu/dept 三域各新增 `POST /{xxx}/{id}/status` 动作接口（动词场景走 POST，符合 API 规范），复用用户域既有模式——实体充血 `changeStatus(target)` 做值域与业务守卫（含 2.2 内置守卫），应用层乐观锁更新。角色域顺带把内置角色不可停用守卫收进实体（当前仅前端禁用）。
- **前端统一**：switch `@change` 调专用接口，失败自动回滚开关显示，loading 防连点；角色页从假开关切换到真接口；api 层用工厂函数封装（`createStatusApi(resource)`），调用侧零差异。
- **不做公共状态接口**：见第 4 节「明确不做的事」——每域独立接口保住声明式鉴权、分域解耦、审计语义三道防线。

### 2.6 排序统一（解 P5，划界方案）

**划界规则一句话：给用户看的顺序才需要排序字段，分页列表不需要。**

| 结构 | sort 字段 | 处理 |
|------|----------|------|
| 树/有序集合（menu、dept、dict_item） | 保留 | 见下 |
| 纯列表（role） | **删除** | DB 字段、DTO/VO、表单项、排序列全去，列表按 `id ASC`（创建序） |

树域（menu/dept/dict_item）方案：**数字字段彻底隐形**——

1. **查询生效**：凡有 sort 的列表/树，一律 `ORDER BY sort ASC, id ASC`（id 兜底稳定序）；菜单域补齐 orderBy，树构建保输入序。后续业务模块照此规范执行。
2. **缺省自动算**：create 时 sort 为空或 0 → 同级（同父级）当前 `max(sort) + 10`（间隔 10 便于中间插入；新节点自然落同级末尾）。
3. **调序用上移/下移**：各树域新增 `POST /{xxx}/{id}/move`（`direction: up|down`）。实现：按 `父级 + sort ASC, id ASC` 取同级列表，**move 时先对该级规范化重排（10、20、30…），再与相邻节点交换**——规范化顺带修复存量全 0 脏数据；事务内两行更新 + 乐观锁，并发移动后到者 409。与 status 接口同一套「动词走 POST」模式。
4. **界面去数字**：表格移除「排序」列，表单移除排序输入框——用户全程不见数字，sort 从输入项退化为实现细节。
5. 不做拖拽（antd Table 树形无原生行拖拽，成本高收益低）与分数排序（LexoRank，杀鸡用牛刀）；将来真有高频批量调序需求再上拖拽，存储层无需变动。

### 2.7 错误码分配约定（追加不插入）

背景：SystemErrorCode 现状 18001-18038 按域连续紧密分配、零预留（用户 18001-18014 / 角色 18015-18018 / 菜单 18019-18023 / 组织 18024-18027 / 字典 18028-18031 / 参数 18032-18034 / 编号 18035-18036 / 日志附件 18037-18038），规划容量 40 已接近用满，且无法在中间插入。

规则一句话：**错误码是不透明标识符，数字顺序不承载语义；新码一律区间 max+1 追加到尾部，域归属靠枚举注释分组 + 文档清单表达，不靠数字连续。**

1. **追加不插入**：已落地模块（system）新错误码一律取 `max + 1`（18039 内置菜单保护、18040 提权守卫，见 2.2/2.1），不做既有码回迁重排——重排收益仅「数字好看」，代价是枚举 + 04 文档 40 条清单 + 集成测试断言 + 前端硬编码全量机械搬迁，零业务价值。
2. **预留用在未开工模块**：采购/销售/库存/生产/财务等尚未开发的模块错误码量大、子域明确（04 文档已规划子块，如财务 16001-16049 / 16350-16399），开工时**第一天就按子域预留号段**，一次到位；system 域不回填预留。
3. **查找靠文档**：04 接口文档 2.10 清单按域分组展示，枚举内保持 `// ---------- 域（起-止） ----------` 注释分组；新码追加时在对应域注释块尾部续写或新开块。

## 3. 实施顺序

按「角色模型 → 菜单保护 → 绕过兜底 → 开关统一 → 文档收尾」排序，每步可独立验证。

### 阶段一：超管角色模型（2.1）

落点：`SysRole` / `SysRoleApplicationServiceImpl` / `UserAccessServiceImpl` / `AdminInitializer` / `SysUserRole` / ErrorCode

1. 种子调整：ADMIN 角色 `role_code='ADMIN'`；新增内置 SYSTEM_ADMIN 角色预勾选全部 /system 菜单（role_menu 种子同步）。
2. 超管判定下沉：access 域提供 `isSuperAdmin(userId)`（is_admin=1 或持有启用 ADMIN 角色），`listMenuTree/listPerms` 及权限装载统一改用。
3. 提权守卫：分配角色接口——目标含 ADMIN 角色时要求操作者为超管（新错误码 18040「仅超级管理员可分配超级管理员角色」）；角色 update 拒绝修改 ADMIN 权限集。
4. AdminInitializer：确保 admin 账号持有 ADMIN 角色（幂等）。
5. 前端：角色列表/用户详情超管标识。
6. 单测 + 集成测试：判定正反例、提权守卫正反例。

### 阶段二：内置菜单保护（2.2）

落点：`sys_menu` 表/schema.sql/种子、`SysMenu`、`SysMenuDomainServiceImpl`、`SysMenuApplicationServiceImpl`、ErrorCode、数据库设计文档

1. 表加 `is_system` 字段，种子 /system 全子树置 1，开发库 ALTER + 数据修复。
2. 实体守卫：停用（含子树检查）、删除拒绝内置节点；错误码 18039。
3. 前端：菜单页内置行开关/删除禁用 + 标签。
4. 单测 + 集成测试。

### 阶段三：admin 绕过 + 启动复位（2.3/2.4）

落点：`UserAccessServiceImpl`、`AdminInitializer`

1. 超管分支全量取菜单（含停用）。
2. 启动复位 is_system 菜单状态 + admin 角色持有。
3. 单测：停用菜单管理入口后超管仍可访问/恢复。

### 阶段四：状态开关 + 排序统一（2.5/2.6）

落点：`SysRole/SysMenu/SysDept` 三域 Controller/Service/Entity、前端四页面、集成测试、schema/数据库设计文档

1. 三域新增 status 动作接口 + 实体守卫 + 单测。
2. 前端菜单/部门页状态列改 switch（内置行禁用），角色页切真接口。
3. 集成测试补三域 status 接口用例。
4. role 域删 sort 字段（DB 列、DTO/VO、表单项、列表按 id ASC）。
5. 树域（menu/dept/dict_item）补 `ORDER BY sort ASC, id ASC`，create 缺省 `max(sort)+10`；各域新增 `POST /{xxx}/{id}/move` 接口（规范化重排 + 相邻交换 + 乐观锁 409）。
6. 前端移除「排序」列与排序输入框，树页面行内加「上移/下移」操作；同层级规范化重排顺带修复存量全 0 脏数据。

### 阶段五：文档同步与回归

1. 数据库设计文档：sys_menu.is_system 字段、SYSTEM_ADMIN 角色种子、role 删 sort、「种子菜单即内置」通用约定、树域 sort 隐形与 move 重排规范。
2. API 设计文档：三域 status / move 接口、新错误码 18039/18040、ADMIN 角色语义；2.10 补充「追加不插入 + 未开工模块按子域预留」分配规则说明（与 2.7 对齐）。
3. 概要/需求文档：三层角色模型表述。
4. 回归清单：自锁场景（普通管理员停用菜单入口→超管可恢复）、提权场景（普通管理员分配 ADMIN 被拒）、内置菜单停用/删除被拒、四页面开关行为一致。

## 4. 明确不做的事

- 不做 path 白名单硬编码保护内置菜单——改 path 即绕过，脆弱；行级 `is_system` 标记是正解。
- 不做超管多级（如二级超管）——三层模型已覆盖当前需求，过度设计。
- 不给普通用户提供「恢复内置菜单」的任何入口——恢复是超管特权 + 启动复位兜底。
- 不做角色继承/层级（RBAC1）——SYSTEM_ADMIN 权限集可改已满足灵活性，引入继承徒增复杂度。
- **不做一套公共 status/move 接口**（如 `POST /api/common/entities/{id}/status`）——三个理由：
  1. **破坏声明式鉴权**：公共接口的 resource 类型退化为参数，`@PreAuthorize` / 注解鉴权只能写模糊的通配，无法按 `/roles/**`、`/menus/**` 精确声明权限点；
  2. **破坏分域解耦**：跨域聚合入口形成新耦合点，各域守卫（内置菜单、内置角色、admin 用户）被迫塞进公共分发逻辑或由各域回调，分层规则（跨域须经 Service 最小接口）被打穿；
  3. **破坏审计语义**：`@AuditLog` 无法区分「停用角色」与「停用菜单」，操作类型/单据号语义丢失。
  各域独立接口是几个 Controller 方法 + Entity 充血守卫的成本，换三道防线完整，且前端用 `createStatusApi(resource)` 工厂后调用侧零重复。

## 5. 验收标准

1. 停用任意菜单（含菜单管理入口）后，超管仍能访问菜单管理页并恢复，普通管理员由超管恢复——自锁死循环在超管层面不可能成立。
2. 内置菜单（含按钮）停用/删除均被后端 18039 拒绝，前端开关/按钮禁用且有提示。
3. 普通管理员给任何用户分配 ADMIN 角色被 18040 拒绝；超管分配成功。
4. 给用户勾「超级管理员」角色即获得全量权限与绕过滤能力；去掉角色即收回——超管身份可授予、可撤销、可区分。
5. 用户/角色/菜单/部门四页面状态列交互一致（switch + 专用接口 + 失败回滚），角色页不再走全量 update 假开关。
6. 树形页面（菜单/部门/字典项）同级顺序按 sort 稳定生效；新增不填排序自动落同级末尾；上移/下移可用且并发冲突返回 409；角色列表无 sort 字段，按创建序展示。
7. `mvn -pl erp-system -am test` 全绿 + `mvn test -Pit -pl erp-bootstrap -am` 全绿 + `pnpm build` 零错误。
8. 数据库设计文档、API 设计文档与实现一致。
